# Harness 工作流

## 1. 先定义任务契约

开始修改前明确：目标、允许修改范围、不可改变的行为、验收标准，以及是否需要真机 BLE 验证。复杂任务使用 `.codex/task-template.md`。

## 2. 评估影响

- 读取关联模块与现有测试。
- BLE、计时、成绩校验、公式 setup 改动必须说明对历史记录、PB/AO 和真机设备的影响。
- 若需求与已知不变量冲突，先停止并解释，不用补丁绕过。

## 3. 最小实现

- 优先新增纯函数和测试，再把结果接入 UI。
- 不修改无关文件；不重写已有可用模块来解决局部问题。
- 用户工作区已有未提交内容视为用户资产，不能覆盖或回退。

## 4. 验证闭环

1. 运行目标单测。
2. 运行 `npm run harness:verify`（跨模块改动必需）。
3. 如涉及页面或服务，确认 `http://localhost:3000/api/health` 可用。
4. 如涉及真实 BLE / 陀螺仪，标记“需真机验证”，不得把模拟结果表述为设备已验证。

## 5. 交付报告

报告按以下顺序给出：结果、修改文件、验证命令及结果、风险或后续真机步骤。
